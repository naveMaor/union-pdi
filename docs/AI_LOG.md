## Multi-agent communication experiment

Before starting Step 1.5, the orchestrator ran a small experiment to verify native agent-to-agent communication before relying on it for real implementation work.

**Setup:** two named background agents were spawned directly from the orchestrator session, `builder` (agent id `abuilder-145cc44dca7535ab`) and `validator` (agent id `avalidator-0e0e661cab25ad12`), each briefed independently (not given each other's reasoning, only each other's name to address messages to).

**What happened, in order:**

1. **builder → validator:** Builder proposed a database constraint to prevent the same vehicle appearing twice in the same daily PDI plan: a PostgreSQL partial unique index on `plan_vehicles(plan_id, vehicle_id) WHERE excluded_at IS NULL`, added via a Sequelize migration, intended to block duplicate *active* membership while letting excluded/historical rows persist across plan regeneration.
2. **validator → builder:** Validator reviewed the proposal independently and sent back five concrete technical points: (1) whether re-adding a previously-excluded vehicle should `UPDATE` the existing row's `excluded_at` rather than `INSERT` a new one, to avoid unbounded row growth; (2) the application must still catch Postgres `23505 unique_violation` for a concurrent-insert race, not rely on the index alone; (3) `plan_id`/`vehicle_id` must be explicit `NOT NULL`, since Postgres treats `NULL`s as distinct in unique indexes; (4) the down-migration must explicitly `removeIndex` the named constraint; (5) whether plan regeneration reuses the same `plan_id` in place or creates a new plan row needs to be confirmed, since that determines whether the index is the actual mechanism preserving exclusions or merely incidental.
3. **builder → validator:** Builder accepted all five points, incorporating (1), (3) and (4) as direct fixes to the design, and flagging (2) and (5) as service-layer/regeneration-design requirements the index alone cannot resolve. Validator confirmed it had no further issues with the revised proposal.

**Result:** direct bidirectional `SendMessage` delivery between two independently-running named agents succeeded — a full round trip (`builder` → `validator` → `builder`) completed with each agent acting only on content it actually received, not fabricated, and no messages were manually relayed by the orchestrator at any point.

**Limitation:** the orchestrator only observed each agent's own self-reported summary of what it sent/received (via idle notifications and direct teammate messages); there is no independent tool available to the orchestrator to inspect a raw message log, so correctness of delivery rests on each agent's own account.

## Architectural concern raised after external review (open, not yet resolved)

After the above experiment, the human developer separately consulted ChatGPT about the same constraint design. That review raised a concern not caught by Builder or Validator at the time: the partial-unique-index approach (`WHERE excluded_at IS NULL`) ties manual-exclusion state directly into the `plan_vehicles` membership table, which may be unnecessary complexity — the assignment (`docs/assignment/SPEC.md`, Section 10) calls for a **separate** manual-exclusions table and a separate decision/event audit log, and does not require plan-version history. A simpler alternative suggested: a plain composite unique constraint on `plan_vehicles(plan_id, vehicle_id)`, with manual exclusions stored in their own table, keyed independently (e.g. by `vehicle_id` + plan date) rather than as a soft-delete flag on plan membership rows.

This is recorded as an **open architectural question to evaluate during Step 1.5 design**, not as an already-resolved defect — no code or migration implementing either design exists yet. Separately, during a later protocol-sync exercise in this same session, the Validator agent — after actually reading `docs/assignment/SPEC.md` directly for the first time — independently raised the same concern on its own, before being told about the ChatGPT review. That independent convergence is noted here as supporting evidence, not as proof the concern is correct; it still needs to be resolved as part of the Builder's Step 1.5 design proposal and Validator's review of it.

## Incident: migration rollback (`db:migrate:undo` ×8) run against the development database

During Builder's post-implementation self-verification (after human approval to implement), Builder ran `db:migrate` → `db:migrate:undo` ×8 → `db:migrate` directly against the existing development database (`union-pdi-db-1` / `union_pdi`), not an isolated test database. The task instructions for this round had told Validator explicitly to test migration rollback "against an isolated disposable test database, not the development database," and separately stated the general rule "do not run destructive commands against the existing development database" — but the orchestrator's message to Builder authorized applying migrations to the existing dev container without explicitly repeating the rollback-isolation rule for Builder specifically.

Investigated directly with Builder (not inferred): Builder reported it did not see an instruction forbidding rollback testing against the dev DB in what was relayed to it, and read its authorization to "apply migrations to the existing dev DB" as also covering rollback testing against that same container. Builder's stated judgment at the time was that the operation was non-destructive in effect because every table was empty (first-ever migration run, no seed data existed yet), so a full drop/recreate carried no data-loss risk — but Builder itself acknowledged, when asked, that it did not weigh whether the instruction was meant to prohibit *any* rollback testing on a shared dev resource regardless of current data state, which is a gap in its reasoning rather than a deliberate, defended choice.

Orchestrator assessment: this was an instruction-scoping gap on the orchestrator's side (the dev-DB-only-for-Validator's-isolation-testing rule was communicated clearly to Validator but not repeated for Builder, and Builder's authorization message didn't explicitly forbid it), compounded by Builder assuming scope rather than asking. No data loss occurred (dev DB had no rows at the time), and the sequence was independently confirmed afterward to have left the dev DB in the correct final state (all 8 tables present, 0 rows). Going forward, orchestrator instructions to any agent performing migration work will explicitly state the isolated-test-DB-only rule for all rollback/destructive testing, not only when relaying it to one agent.

## Human-discovered CORS defect (pre-Task 7)

During manual Chrome testing against the disposable demo database (`docs/DEMO_DB.md`, demo backend on port 3002, Vite on 5173), the human found a real cross-origin failure: `DELETE /api/vehicles/PDI-023/blocker` from `http://localhost:5173` failed its preflight, because `Access-Control-Allow-Methods` did not include `DELETE`.

Root cause, confirmed directly in `node_modules/@fastify/cors` (v11.4.3): `app.register(cors, { origin: 'http://localhost:5173' })` in `server/src/app.js` never set a `methods` option, so the plugin fell back to its own default, `GET,HEAD,POST`. Every `DELETE` route (blocker removal, exclusion cancellation) and the `PUT /api/settings` route were silently unreachable from a real browser, even though the routes themselves worked correctly when called same-origin or from Node.

Fix: `server/src/app.js` now registers CORS with an explicit `methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE']`, alongside the existing restricted `origin`. No other app.js behavior changed.

Why the retained Chrome verifier (`client/scripts/verify-batch-b2.cjs`) never caught this: its `api()` helper (used for most state setup, including blocker POST/DELETE and settings PUT) calls `fetch` directly from the Node test process against the Fastify server's own listen address — Node's `fetch` does not enforce CORS, so no preflight was ever exercised there. Separately, the one Vite dev server the verifier drives through the real browser is configured with `proxy: { '/api': apiUrl }`, so the UI's own `fetch` calls go through Vite's same-origin dev proxy rather than hitting the Fastify origin directly. Neither path reproduces what a real, unproxied `http://localhost:5173` → `http://localhost:3002` browser request does. The verifier was not touched this round; its gap (no direct-origin, preflight-enforcing browser request) is a known limitation to consider for Batch 7B or later.

## Demo Reset feature — implemented, tested, verified (Orchestrator only, no agents)

Implemented the approved proposal directly, with several additional hardening requirements the human added on approval: fail closed on a missing/weak token, concurrency protection against *ordinary business mutations* (not only against a second concurrent reset), rate-limiting of *failed authentication attempts* separately from successful resets, and permission to leave the feature enabled for the whole recruitment window rather than toggling it off after each use.

**Concurrency design, and why a single lock wasn't enough.** Inspection found `planService.js` already had a per-plan-date advisory lock (`acquirePlanLock`), reused by all four plan-mutating functions and, via `planEditService.js`, by its four functions too. But `blockerService.js` (vehicle blockers) and `settingsService.js` (Admin parameters) had no lock at all — they mutate tables the reset also rewrites, so "protect against normal business mutations" meant more than the plan-date lock covered. Rather than inventing a parallel locking scheme, `acquireBusinessMutationLock` (a shared advisory lock on one fixed key) was added once in `planService.js` and wired into `acquirePlanLock` itself — meaning the 7 plan/plan-edit functions got the new protection for free with zero changes to their own code — plus two new explicit call sites in `blockerService.js` and one in `settingsService.js`. The reset acquires the same key in exclusive mode (via a second, separate advisory-lock key reserved purely for reset-vs-reset mutual exclusion, checked with a non-blocking try-lock first so two concurrent resets fail fast against each other rather than one silently queuing behind the other for an unbounded time).

**A genuine finding, not just a refinement of the earlier proposal:** the original proposal already flagged that `audit_events.event_type` has a real database-level `CHECK` constraint, not just Sequelize-level validation — confirmed during implementation by reading the actual migration file, and handled with a dedicated new migration (`20261127140000-add-demo-reset-audit-event-type.js`) that drops and recreates the constraint, rather than only updating the model's `validate.isIn` array (which alone would have let the application-level check pass while the database itself still rejected every `DEMO_RESET` insert).

**Reusing, not duplicating, seed logic:** `seed.js` was changed only by exporting `CSV_PATH`, `DEFAULT_SETTINGS`, `DEFAULT_BRAND_QUOTAS` and `DEFAULT_SHIPPING_CAPACITIES` it already defined internally — no behavior change to seeding itself. The reset service calls `parseVehiclesCsv()` directly and restores every vehicle column in a single `bulkCreate(..., { updateOnDuplicate: [...] })` upsert, rather than writing a second, parallel CSV-parsing implementation.

**Frontend:** the Admin screen's new "Demo Data Reset" section requires both a hand-typed token (password input, cleared immediately after every attempt whether it succeeds or fails, never pre-filled, never written to any browser storage) and an exact Hebrew confirmation phrase before the reset button even becomes clickable, and then a second, separate confirmation dialog (reusing the existing `PlannerDialog` component and the same interaction pattern as the screen's pre-existing "discard unsaved changes" dialog) before the request is actually sent.

**Ten tests, not seven** — the three the human specifically asked for beyond the original seven: a failed-token lockout test (five wrong attempts lock out the endpoint for a cooldown window, even against the *correct* token afterward, proving the attempt-based rate limit is independent of the per-reset one); a concurrent-business-mutation test (`blockerService.addBlocker` fired at the same time as a reset, asserting the vehicle ends up in one fully consistent state — either the reset's CSV value or the blocker on top of it — never a torn write); and a transaction-rollback test (dropping `audit_events` immediately before the reset's own final insert into it, proving the entire transaction — including the vehicle/settings restoration that already happened earlier in the same transaction — rolls back completely on failure). One test-writing mistake was caught and fixed before any of this ran green: an early version of the "missing confirmation" test accidentally destructured `{ confirm: undefined }` against a parameter default of `'RESET_DEMO_DATA'`, which (correctly, per plain JavaScript default-parameter semantics) substituted the default and silently tested the *success* path instead of the missing-confirmation path; caught by the test itself still passing when it should have failed, fixed with an explicit `omitConfirm` flag instead of relying on `undefined`.

**Verification, all against real disposable, CSV-seeded PostgreSQL databases, never the shared development database:** full backend suite 110/110 (100 pre-existing, unchanged, plus the 10 new tests); clean `npm run build` and `npm run lint`; the complete retained `verify-batch-b2.cjs` Chrome verifier re-run end to end with every existing scenario still passing (a stray leftover test database from an unrelated, previously interrupted test run was found and dropped during this check, not caused by this work); and a new, focused, disposable-DB Chrome verification written specifically for the new UI — confirming the reset button's enable/disable logic, a rejected wrong-token attempt's exact Hebrew error message with zero state change, and a correct reset's visible success message backed by an actually-verified `plan: null` / 300-vehicle / default-settings database state, with zero browser console errors throughout. Development database fingerprints (all 8 tables) were confirmed unchanged before and after this entire round.

## Human-caught defect: the new migration was never applied outside disposable test databases

The human manually tested the feature against their own locally-running server (not through any script of mine) and hit `new row for relation "audit_events" violates check constraint "audit_events_event_type_check"` — a real defect in the deployment/operational story, not in the reset logic itself. All of this session's own verification had run the migration only inside disposable, freshly-created test databases (`demoResetRoutes.test.js`, the focused Chrome scripts), which always start from an empty schema and apply every migration including the new one — so this gap was invisible to every automated check performed so far, and could only have been caught by someone actually running the persistent local server, which the human did.

Fixed in two steps, each surfaced by the human's own further manual retesting rather than assumed fixed after the first fix:
1. Ran `db:migrate` against the real local development database (`union_pdi`) — confirmed via `pg_get_constraintdef` that the constraint now includes `DEMO_RESET`, and that `vehicles`/`plans` row counts were unaffected (a purely additive schema migration).
2. The human retested and hit the *same* error again. Investigated rather than assumed a fluke: the human's manual test was actually running against `union_pdi_demo` (the separate, disposable demo database documented in `docs/DEMO_DB.md`'s `npm run demo` workflow), a database this session had never touched. Ran the same migration against it too, then — at the human's request — ran the full reset flow myself end-to-end against a locally-started server configured exactly as the human's (`DEMO_RESET_ENABLED=true`, `DEMO_RESET_TOKEN` matching the human's chosen value, `POSTGRES_DB=union_pdi_demo`): wrong token correctly rejected with `403`, correct token succeeded with `200 {"vehicleCount":300}`, and the plan (previously `APPROVED` with a returned note) correctly ended at `null`. Confirmed the real development database (`union_pdi`) was never touched by any of this.

This is recorded as a genuine operational gap this session's own automated verification could not have caught by construction (disposable test databases don't have "forgot to migrate" as a failure mode) — it took the human actually running the persistent server to find it, and a second round of manual testing to find the second instance of the same root cause.
